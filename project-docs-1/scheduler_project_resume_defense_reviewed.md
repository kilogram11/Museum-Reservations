> 用途：简历、晋升/项目答辩、技术面试素材

## 一、本次工作的准确定位

本次工作从零实现了一套**基于 Redis ZSET 的轻量级定时调度内核**，核心目标是将“任务何时到期”与“到期后谁优先执行”拆成两个阶段，并支持多 Worker 并发消费、HTTP/gRPC 下游调用、多种调度语义、失败重试、策略降级、生命周期事件、管理端接口以及较完整的测试链路。

相比直接依赖简单定时注解或把下游调用逻辑散落在业务代码中，这套实现提供了一个相对独立的调度执行层：任务先进入时间线，到期后推进到执行线，再由 Worker 竞争消费并调用下游动作。

需要特别说明的是：

- 当前材料能够证明的是：**多 Worker 可以并发竞争消费执行队列中的任务**。
- 当前材料不能证明：完整的多实例 Leader Election、故障接管、fencing token、跨实例高可用等能力。
- 因此更准确的称呼是：**轻量级定时调度内核 / 调度服务**，而不是直接宣称“成熟的分布式调度平台”。
- 当前材料也不能证明 exactly-once、任务绝不丢失或端到端强一致性。

## 二、工作背景

项目需要支持按时间触发任务，例如一次性执行、固定间隔、Cron 周期执行、固定延迟执行等，同时还需要将实际动作调用统一抽象出来，以便兼容不同下游协议。

从代码变更可以确认，原有方案需要解决几个核心问题：

1. 需要统一处理多种调度语义，而不是把定时逻辑分散在不同业务代码中。
2. 需要同时支持 HTTP 和 gRPC 下游调用，并减少每接入一个新服务时重复编写协议处理、超时判断、错误分类等逻辑。
3. 需要将“任务是否已经到期”和“到期任务的执行优先级”拆开处理。
4. 需要在 Redis 客户端不支持 `ZPOPMIN`、同时不能使用 Lua 的约束下，实现多个 Worker 对优先级队列的安全竞争消费。
5. 调度类代码涉及并发、Redis 状态、后台线程和网络协议，仅靠简单单元测试不足，需要更完整的集成与端到端验证。

根据当前材料，可以合理推断该实现的目标是构建一个**自主可控、轻量、可扩展的调度执行层**，而不是替代完整的企业级调度平台。

## 三、我的具体工作

### 1. 设计 timeline / executeline 双阶段调度模型

使用两个 Redis ZSET 承担不同职责：

```text
timeline ZSET
score = 下一次触发时间
        ↓
TimeLineTrigger
        ↓
executeline ZSET
score = 执行优先级
        ↓
多个 TaskWorker
        ↓
Action
```

其中：

- `timeline` 负责回答“任务什么时候到期”；
- `executeline` 负责回答“已经到期的任务，谁应该先执行”；
- 单线程扫描 timeline，将到期任务批量推进到 executeline；
- 多个 Worker 从 executeline 中竞争消费任务并执行。

这一拆分避免了执行耗时直接阻塞时间线扫描，同时为到期任务增加了独立的优先级维度。

### 2. 在受限 Redis 能力下实现并发安全竞争消费

执行队列需要支持多个 Worker 并发抢占优先级最高的任务。

由于：

- Redis 客户端版本不支持 `ZPOPMIN`；
- 运行环境又禁止 Lua；

因此无法直接使用原生命令或 Lua 脚本完成“读取最小成员并删除”的原子操作。

实现采用：

```text
WATCH
↓
ZRANGE 0 0
↓
MULTI
↓
ZREM
↓
EXEC
↓
冲突则重试
```

利用 Redis 乐观事务实现竞争控制：

- Worker 先 WATCH 目标 ZSET；
- 读取当前最小成员；
- 在事务中执行删除；
- 如果期间 ZSET 被其他 Worker 修改，`EXEC` 失败；
- 当前 Worker 重新竞争；
- 设置最大重试次数避免无限冲突。

该实现解决的是**多个 Worker 不同时成功消费同一个 ZSET 成员**的问题。

需要注意，这不等价于 exactly-once。Worker 成功移除任务后宕机、下游执行成功但响应超时等场景，仍然需要结合幂等、补偿或额外状态机制讨论。

### 3. 实现多种调度语义

支持：

- once：执行后不再继续调度；
- interval：按固定周期计算下一次触发；
- cron：基于 Cron 表达式计算下一次执行时间；
- fixed_delay：以上一次实际执行完成时间为基准，再增加指定延迟。

其中 fixed_delay 使用：

```text
nextTrigger = finishTime + delay
```

而不是简单基于上一次计划触发时间计算，因此符合“上一轮执行完成后再等待 N 毫秒”的语义。

这里不应包装成复杂算法创新，它更准确地属于：**正确实现了不同定时语义之间的时间基准差异**。

### 4. 统一 HTTP / gRPC 下游调用抽象

调度核心不直接绑定具体通信协议，而是通过统一 Invoker 接口调用下游。

实现包括：

- 根据 handler 类型选择 HTTP / gRPC 实现；
- HTTP 层统一处理请求构造、状态码分类、超时、可重试/不可重试错误；
- gRPC 通过 `service + method` 路由到对应适配器；
- 新增 gRPC 下游时，通过新增适配器接入，而无需修改核心调度执行流程；
- gRPC Channel 按 target 做复用；
- 对未知协议使用 Unsupported 实现明确失败，而不是返回 `null`。

真正值得强调的不是“用了工厂、策略、适配器、空对象四种设计模式”，而是：

> **将调度核心与具体协议、具体下游实现解耦，使新增协议适配或新增 gRPC 服务时尽量不修改核心调度流程。**

### 5. 实现优先级策略与降级

任务进入 executeline 前可以通过外部 Policy 获取优先级。

如果外部 Policy 调用失败：

- 不阻断主调度流程；
- 不进行重复重试；
- 降级到内置优先级；
- 标记降级状态，供后续日志或事件追踪。

这一设计的核心价值是：**优先级策略属于增强能力，而不是主链路的硬依赖**。

### 6. 增加生命周期事件与可观测性扩展点

围绕任务生命周期定义事件，包括注册、推进、入队、执行开始、执行成功/失败、写回、取消等。

事件监听器之间做异常隔离，避免单个监听器异常影响调度主链路。

这一部分的价值主要是：

- 让调度过程具备较明确的状态观测点；
- 后续可以接日志、指标、告警、审计；
- 调度核心不直接耦合具体观测实现。

### 7. 建立调度内核测试链路

测试不只停留在 Mockito 单元测试，还覆盖：

- Controller / Service / Kernel / Policy / Invoker 单元测试；
- 真实 Redis 集成测试；
- once / interval / fixed_delay 等内核 E2E；
- gRPC in-process server 协议测试；
- HTTP 协议测试；
- Redis key 前缀隔离和并发资源控制。

其中 gRPC 使用 in-process server/channel，避免真实端口竞争，同时保留真实 protobuf / stub 调用路径。

这部分是整个项目较有价值的工程亮点之一。

## 四、真正值得强调的三个技术亮点

### 亮点一：Redis 受限环境下的并发安全竞争消费

这是当前项目最有技术含量的部分。

问题不是简单“从 ZSET 取一个任务”，而是：

```text
多个 Worker
      ↓
同时读取优先级最高任务
      ↓
必须保证同一个 ZSET member 不被多个 Worker 同时成功消费
```

常规情况下可以直接使用 `ZPOPMIN` 或 Lua，但当前环境两者都不可用。

因此使用 Redis：

```text
WATCH + ZRANGE + MULTI/ZREM + EXEC
```

实现乐观并发控制。

这一点可以重点体现：

- Redis 事务语义理解；
- 并发竞争处理；
- CAS / optimistic locking 思维；
- 冲突重试；
- 受限基础设施下的工程替代方案。

#### 面试中必须主动承认的边界

该方案解决的是“竞争消费”的原子性问题，不应该扩大成：

- exactly-once；
- 端到端不重复；
- 任务永不丢失。

如果 Worker 成功 ZREM 后宕机，或者 Action 实际成功但响应超时触发重试，仍然可能产生丢失或重复执行风险，需要下游幂等、任务状态机或补偿机制进一步解决。

---

### 亮点二：timeline / executeline 双阶段调度模型

将：

```text
什么时候执行
```

和：

```text
到期后谁先执行
```

拆成两个独立维度。

timeline：

```text
score = trigger timestamp
```

executeline：

```text
score = execution priority
```

这比单一按时间排序的队列更适合同时表达：

- 定时触发；
- 到期任务积压；
- 优先级调度；
- 多 Worker 并发执行。

准确的价值描述应该是：

> 将到期判定与实际执行解耦，避免慢任务直接阻塞时间线扫描，同时允许到期任务独立进行优先级排序。

不建议使用：

> “调度精度不受执行速度影响”

这种绝对化表述，因为 Worker 饱和后，实际执行时间依然会受到执行能力影响。

### 亮点三：针对状态型调度内核建立完整测试链路

调度系统最容易出问题的部分集中在：

- 时间；
- 并发；
- Redis 状态；
- 后台线程；
- HTTP / gRPC；
- 重试；
- 环境隔离。

因此项目不仅使用单元测试，还通过：

```text
Unit Test
    ↓
Redis Integration Test
    ↓
Kernel E2E
    ↓
HTTP / gRPC Protocol Test
```

覆盖核心执行路径。

其中 gRPC in-process 测试是一项值得保留的工程实践：

- 不占真实端口；
- CI 中不会因为端口冲突不稳定；
- 仍然经过真实 protobuf / stub 调用路径；
- 比纯 Mock 更接近真实协议行为。

## 七、当前项目必须承认的架构边界

如果在答辩或面试中讲这个项目，以下问题必须提前准备。

### 1. Worker pop 后宕机

```text
ZREM executeline 成功
↓
Worker 宕机
↓
Action 尚未调用
```

当前材料没有证明存在恢复机制。

因此不能承诺任务绝不丢失。

### 2. Action 已成功，但响应超时

```text
Action 实际执行成功
↓
网络超时
↓
Scheduler 判断失败
↓
Retry
↓
Action 再次执行
```

如果下游没有幂等，可能产生重复副作用。

因此不能承诺 exactly-once。

### 3. timeline → executeline Pipeline 的半失败

批量推进为了吞吐使用 Pipeline，而不是每个 member 单独事务。

需要明确：

- ZREM 和 ZADD 的具体顺序；
- 某条命令失败后的状态；
- 是否存在任务同时出现在两条线；
- 是否存在任务从两条线都消失；
- 下一轮重试是否一定能恢复。

当前材料只能证明这是一个有意识的吞吐/原子性 trade-off，不能证明所有失败场景都已经完全闭环。

### 4. 多实例 Scanner 协调

材料中出现“单 leader”假设，但没有看到：

- Leader Election；
- Lease；
- Heartbeat；
- Fencing Token；
- Failover。

因此不建议直接宣称完整的“分布式高可用调度平台”。

### 5. 高优先级任务是否会导致 starvation

如果高优先级任务持续进入 executeline，低优先级周期任务是否可能长期得不到执行，需要明确是否存在 aging / fairness 机制。

# 八、答辩版本

这次工作主要是从零实现了一套基于 Redis ZSET 的轻量级定时调度内核。我的核心设计是把调度拆成两个阶段：timeline 只负责判断任务什么时候到期，score 使用下一次触发时间；任务到期后再推进到 executeline，executeline 使用执行优先级作为 score，由多个 Worker 并发消费。这样把“时间触发”和“执行优先级”两个维度解耦，避免慢任务直接阻塞时间线扫描，同时为到期任务提供独立的优先级排序能力。

实现过程中比较有挑战的一点是执行队列的并发消费。当前 Redis 客户端不支持 ZPOPMIN，同时运行环境又不能使用 Lua，所以没法直接完成原子的“读取最小成员并删除”。我最后使用 WATCH、ZRANGE、MULTI/ZREM、EXEC 组合成乐观事务：多个 Worker 同时竞争时，只有一个 Worker 能成功提交删除，其他 Worker 因 WATCH 检测到 key 被修改而失败并重新竞争。这个方案解决了多个 Worker 同时拿到同一个执行队列成员的问题。

另外，我将下游动作调用抽象为统一 Invoker，分别支持 HTTP 和 gRPC，并通过注册式适配器降低新增 gRPC 下游时对核心调度代码的修改范围。针对调度类代码容易出现的时间、并发、Redis 状态和网络协议问题，我同时建立了单元测试、真实 Redis 集成测试、内核 E2E 以及 HTTP/gRPC 协议级测试链路，其中 gRPC 使用 in-process server，避免测试端口竞争。

这个版本我没有把它定义成完整的生产级分布式调度平台，因为当前实现仍然存在明确边界，例如 Worker 成功弹出任务后宕机的恢复、Action 成功但响应超时导致重复调用、批量 timeline→executeline 推进的部分失败一致性，以及多实例 Scanner 的 Leader 协调等问题。当前版本更准确的定位是一个具备并发调度、协议适配和较完整测试体系的轻量级调度内核。

# 九、面试讲述版本

我之前做过一个比较完整的定时调度模块，核心场景是把不同业务的定时任务统一收敛到一个调度执行层，而不是让每个业务自己写定时线程和下游调用逻辑。

我当时首先把调度拆成了两个 Redis ZSET。第一个叫 timeline，用下一次触发时间作为 score，只负责判断任务什么时候到期；任务到期后会被推进到第二个 executeline，executeline 再使用任务优先级做 score。多个 Worker 只从 executeline 里竞争执行。这样“时间调度”和“实际执行”就分开了，比如两个任务同时到期，也可以根据优先级决定谁先执行。

实现时最大的一个限制是，我们使用的 Redis 客户端版本没有 ZPOPMIN，同时环境又不允许 Lua，但多个 Worker 又必须安全地从 executeline 里抢任务。我最后用了 WATCH + ZRANGE + MULTI/ZREM + EXEC 来模拟竞争消费：Worker 先 WATCH 队列，读取优先级最高的成员，再通过事务删除；如果这期间其他 Worker 先修改了队列，那么当前 Worker 的 EXEC 会失败，然后重新竞争。这个方案能够保证多个 Worker 不会同时成功消费同一个 ZSET member。

调度核心之外，我又做了一层统一 Invoker，把 HTTP 和 gRPC 调用隐藏在接口后面。特别是 gRPC，通过 service + method 找对应适配器，新接一个下游服务时主要新增适配器，不需要修改 Worker 的执行逻辑。

测试方面我没有只做 Mock 单测，因为这种系统真正难测的是 Redis 状态、并发和时间。我补了真实 Redis 集成测试、几种调度类型的内核 E2E、HTTP 测试以及 gRPC in-process server 测试。

这个项目我现在会比较谨慎地描述成“轻量级调度内核”，而不是直接说成生产级分布式调度平台。因为如果继续往生产级做，还需要解决 Worker 弹出任务后宕机怎么恢复、Action 成功但响应超时导致重复执行怎么处理、批量队列迁移半失败如何补偿，以及多实例 Scanner 如何做 Leader Election 等问题。这些也是我后来复盘这个方案时认为最重要的架构边界。

# 十一、简历标准 Bullet 版本

- 基于 Redis ZSET 设计 timeline / executeline 双阶段调度模型，将“任务到期判定”与“优先级执行”解耦，支持 once、interval、cron、fixed-delay 等调度语义及多 Worker 并发执行。
- 在 Redis 客户端不支持 `ZPOPMIN` 且 Lua 不可用的环境约束下，使用 `WATCH + ZRANGE + MULTI/ZREM + EXEC` 乐观事务实现执行队列的并发安全竞争消费，并增加冲突重试与异常隔离机制。
- 抽象统一的 HTTP/gRPC Invoker 与 gRPC Adapter Registry，使调度核心与具体协议及下游服务解耦，降低新增下游调用适配时对核心执行链路的修改范围。
- 建立覆盖单元测试、真实 Redis 集成测试、调度内核 E2E、HTTP/gRPC 协议测试的验证链路，并使用 gRPC in-process server 减少 CI 端口依赖与测试不稳定性。

# 十二、简历技术型版本

- 设计基于 **Redis ZSET** 的双阶段调度内核：timeline 以 trigger timestamp 排序，executeline 以 execution priority 排序，通过单线程到期扫描 + 多 Worker 并发执行解耦时间调度与任务消费。
- 针对 Redis 客户端无 `ZPOPMIN`、运行环境禁用 Lua 的限制，使用 **WATCH / MULTI / EXEC** 乐观事务组合实现优先级任务的竞争式原子删除，并通过有限重试处理并发冲突。
- 统一封装 **HTTP / gRPC Invoker**，gRPC 使用基于 `service + method` 的 Adapter Registry 进行二级路由，并复用 Channel，降低协议差异对 Scheduler Kernel 的侵入。
- 支持 once / interval / cron / fixed-delay 调度策略，并对外部优先级 Policy 设计 fallback，避免策略服务异常阻断主调度链路。
- 构建 **Unit + Redis Integration + Kernel E2E + HTTP/gRPC Protocol Test** 多层测试体系，gRPC 采用 in-process server/channel 完成协议级真实验证。

# 十三、亮点候选池

## 亮点 1：受限 Redis 环境下实现多 Worker 竞争消费

**技术事实：**  
在 Redis 客户端不支持 `ZPOPMIN`、Lua 不可用的条件下，通过 WATCH + ZRANGE + MULTI/ZREM + EXEC 模拟优先级队列的竞争式弹出。

**解决的问题：**  
多个 Worker 并发读取相同 ZSET 最小成员时，避免多个 Worker 同时成功消费同一个 member。

**价值：**  
体现对 Redis 事务、乐观锁、并发冲突和失败重试机制的理解。

**适合用于：**  
简历 / 技术面试 / 答辩

**可信度：**  
高

**注意边界：**  
不能扩展描述为 exactly-once 或任务绝不丢失。

---

## 亮点 2：timeline / executeline 双阶段调度模型

**技术事实：**  
timeline 按触发时间排序，executeline 按执行优先级排序；扫描线程负责推进，多 Worker 负责执行。

**解决的问题：**  
单一时间队列难以同时表达“什么时候触发”和“到期后谁优先执行”。

**价值：**  
将到期判定与实际执行解耦，为优先级调度和多 Worker 执行提供独立层次。

**适合用于：**  
简历 / 答辩 / 系统设计面试

**可信度：**  
高

**注意边界：**  
不能描述为“执行速度完全不影响调度精度”。

---

## 亮点 3：调度内核多层测试体系

**技术事实：**  
同时存在单元测试、真实 Redis 集成测试、内核 E2E、HTTP 测试和 gRPC in-process 协议测试。

**解决的问题：**  
调度系统依赖时间、并发、后台线程和 Redis 状态，纯 Mock 测试无法覆盖真实行为。

**价值：**  
提高核心调度链路的可回归性，减少并发和协议层问题只在线上暴露的概率。

**适合用于：**  
简历 / 答辩 / 面试

**可信度：**  
高

---

## 亮点 4：HTTP / gRPC 协议解耦

**技术事实：**  
调度核心依赖统一 Invoker；gRPC 再通过 service + method 找对应 Adapter。

**解决的问题：**  
避免 Worker 直接依赖具体协议或下游服务 stub。

**价值：**  
新增下游适配时减少核心执行代码改动。

**适合用于：**  
答辩 / 面试 / 简历次要 Bullet

**可信度：**  
高

---

## 亮点 5：外部 Policy 的非关键路径降级

**技术事实：**  
外部优先级 Policy 调用失败后不阻断调度主流程，而是回退本地优先级并记录 degraded 状态。

**解决的问题：**  
增强能力故障不应导致主链路不可执行。

**价值：**  
体现主链路和增强能力之间的依赖等级设计。

**适合用于：**  
答辩 / 面试

**可信度：**  
高

---

## 亮点 6：生命周期事件扩展点

**技术事实：**  
围绕注册、推进、入队、执行、回写、取消等阶段发布事件，监听器之间异常隔离。

**解决的问题：**  
调度链路状态不透明，后续监控、日志、告警难以解耦接入。

**价值：**  
为可观测性和后续扩展提供统一入口。

**适合用于：**  
答辩 / 面试

**可信度：**  
中高

---

## 亮点 7：fixed-delay 语义正确实现

**技术事实：**  
fixed-delay 使用实际 finish time + delay 计算下一次触发。

**解决的问题：**  
避免把 fixed-delay 错误实现为固定周期。

**价值：**  
保证调度语义正确。

**适合用于：**  
面试细节补充

**可信度：**  
高

**备注：**  
这是正确实现，不属于很强的架构创新。

# 十六、不建议使用的表述

不建议写：

> 设计并实现成熟的企业级分布式调度平台。

当前材料不足以支撑高可用、多实例协调和完整故障恢复。

不建议写：

> 保证任务 exactly-once 执行。

当前材料没有证明端到端 exactly-once。

不建议写：

> 保证任务绝不丢失。

Worker pop 后宕机等 crash window 尚未从材料中得到解决证明。

不建议写：

> 调度精度完全不受执行速度影响。

Worker 饱和后实际执行时间仍然会被执行能力影响。

不建议写：

> 四种设计模式联动，充分贯彻开闭原则。

设计模式数量本身不是成果，而且容易被追问是否过度设计。

更好的表达是：

> 通过统一 Invoker 与注册式 Adapter 将核心调度逻辑与具体通信协议解耦。

# 十七、最终推荐主线

如果未来答辩、面试和简历只能讲一条主线，建议按下面顺序：

```text
为什么需要统一调度
        ↓
为什么拆成 timeline / executeline
        ↓
多个 Worker 如何竞争消费
        ↓
为什么不能用 ZPOPMIN / Lua
        ↓
WATCH + MULTI/EXEC 如何解决
        ↓
HTTP / gRPC 如何与调度核心解耦
        ↓
如何测试 Redis + 并发 + 协议
        ↓
当前方案还有哪些可靠性边界
```

这条线比“我做了 7 个页面、4 个 Controller、用了 4 种设计模式、写了 1 万多行代码”更有技术说服力。

真正值得你重点准备的不是再包装更多亮点，而是把以下四个 Trade-off 讲透：

1. **竞争消费原子性 vs 端到端执行语义**
2. **Pipeline 吞吐 vs timeline/executeline 转移原子性**
3. **多 Worker 并发能力 vs 高竞争下 WATCH 冲突**
4. **轻量级自研调度内核 vs 完整分布式调度平台的能力边界**

如果能够清晰解释这四件事，这个项目在面试中的价值会明显高于简单描述功能列表。
