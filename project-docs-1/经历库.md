## 携程集团 大住宿事业群 Java 后端开发实习

### 基本信息

- 组织：携程集团，大住宿事业群。
- 角色：Java 后端开发实习生。
- 时间：2026.06 - 2026.08。
- 业务领域：酒店业务轻量级定时调度器。
- 技术栈：Spring Boot、Trip FX、CDubbo、CRedis、Redis ZSET/HASH、SOA/REST、HTTP/gRPC、CAT、TripLog。
- 关系类型：实习，必须与项目经历分开呈现。
- 来源：`1.md`、`D:\Users\peiyaowan\aaa_work\Schedule\schedulertest\README.md`、`内核设计.md`、`基于Redis的分布式定时调度器介绍.md`、`留用答辩口播与问答.md`、源码与测试文件。

### 整体背景和目标

酒店业务存在价格刷新、库存同步、策略计算等异步或定时任务场景，需要统一任务注册、按时触发、优先级执行、失败重试和运维观测能力。项目通过 Spring Boot + Trip FX + CDubbo 暴露 SOA 服务，使用 CRedis 的 ZSET/HASH 构建轻量级调度内核，支持 HTTP/gRPC 外调业务 Action。

### 发生了什么：调度内核建模

#### 为什么开始

任务系统需要同时解决“何时触发”和“按什么优先级执行”的问题。如果直接把定时和执行混在一条队列中，会让任务推进、优先级排序和失败处理互相耦合。

#### 用户做了什么

- 参与设计 `timeline` + `executeline` 双队列模型。
- 使用 Redis ZSET score 分别表达任务触发时间和执行优先级。
- 通过 TimeLineTrigger 将到期任务推进到 executeline，通过 TaskWorker 消费并回写执行结果。
- 支持 once、interval、cron、fixed_delay 四类调度语义。

#### 直接产出

- 调度主链路：任务注册 -> timeline 等待 -> 到期推进 -> executeline 执行 -> Action 调用 -> fixed_delay callback。
- 任务配置通过 `typeconfig` HASH 管理，按 action_id 读取调度策略、Action handler 和可选 Policy handler。

#### 后续情况

源码与文档显示主链路已完成，README、AGENT 和 IMPLEMENTATION_PLAN 均记录 TimeLineTrigger、TaskWorker、SOA 接口、VI 点火、监控等能力已落地。

### 发生了什么：高并发推进与一致性

#### 为什么开始

大量任务可能在同一时间到期，需要让系统快速从 timeline 推进到 executeline，同时避免重复推进或脏数据。

#### 用户做了什么

- 使用 Redis `MULTI/EXEC` 保证 timeline 到 executeline 的状态迁移一致性。
- 对大量到期任务引入批量推进路径，降低 Redis 往返开销。
- 在 executeline 弹出时使用 WATCH + MULTI/ZREM 等方式实现原子 pop。

#### 直接产出

- 到期任务可批量从 timeline 转入 executeline。
- 调度和执行分离后，TimeLineTrigger 负责推进，TaskWorker 负责消费。

#### 发生后的结果

- 答辩材料记录：2 核 4G FAT 环境，5 万个 once 任务同时到期，8 线程 Worker 约 45s 排空，消费吞吐约 1100 task/s，timeline/executeline 推进峰值可达 25000+/s。
- 该组数据的边界：Action 为 mock、近 0 延迟；线上实际吞吐会受下游 Action P99 影响。

### 发生了什么：执行链路、策略降级与运维闭环

#### 为什么开始

调度器需要接入不同业务 Action，并让运维侧能注册、取消、查看任务和定位执行状态。

#### 用户做了什么

- 封装 HTTP/gRPC Action 调用和 Policy 动态算分机制。
- 当 Policy 外调失败、超时或返回非法时，降级为内置默认优先级，保证主调度链路不中断。
- 建设任务创建、查询、取消、详情定位、Dashboard、Monitor 等控制台能力。
- 沉淀自动化测试，覆盖异常、边界、降级和并发场景。

#### 直接产出

- SOA 接口包括 `putTypeConfig`、`registerTask`、`cancelTask`、`getTask`、`listTasks` 等。
- Admin REST 提供 timeline/executeline 监控和 Dashboard 聚合。
- README 与代码显示项目包含 CAT Transaction/Event、TripLog、调度事件体系。

### 结果和数据

- Worker 消费吞吐约 1100 task/s。

## 博物馆预约管理与 AI 助手平台

### 基本信息

- 项目：博物馆预约管理与 AI 助手平台。
- 类型：项目经历。
- 技术栈：Spring Boot 3、Java 17、MyBatis-Plus、MySQL、Redis、Lua、Spring AI、DeepSeek、Vue 3、微信小程序、ONNX Runtime。
- 系统形态：微信小程序、Vue 管理端、Spring Boot 后端。
- 来源：`1.md`、`project-docs-1/README.md`、`ARCHITECTURE.md`、`FLOWS.md`、`API.md`、`docs/ai-agent-design.md`、`docs/ai-rag-design.md`、`docs/jmeter/README.md`、源码。

### 整体背景和目标

项目面向博物馆预约、核销、馆规咨询和运营管理场景，用户侧支持场馆/活动浏览、预约下单、二维码入馆、预约记录、AI 咨询与文物识别；管理侧支持排期配置、预约核销、黑名单、公告、统计看板和 Excel 导出。

### 发生了什么：AI 预约 Agent

#### 为什么开始

预约系统中的“查票、下单、取消”和“馆规问答”性质不同：前者必须复用业务链路和权限校验，后者需要检索馆规/公告内容。如果让模型自由生成或直接读写数据，会产生越权、编造或绕过校验的风险。

#### 用户做了什么

- 设计并落地单 Agent + 双 ChatClient + 5 Tool 的预约助手架构。
- 将预约查询/下单/取消与馆规问答拆分为不同链路。
- 封装 `queryDays`、`queryTimes`、`submitBooking`、`listRecords`、`cancelBooking` 五个 Tool。
- Tool 层复用真实预约 Service，避免 AI 绕过业务校验直接读写数据。

#### 直接产出

- 预约助手可以查询可预约日期、查询时段余票、提交预约、列出预约记录、取消预约。
- 写 Tool 通过 UserContext(ThreadLocal) 读取 JWT 登录态，不接受模型传入的外部 userId。

### 发生了什么：RAG 与安全治理

#### 为什么开始

馆规和公告属于知识问答内容，需要降低模型编造风险，同时不能让 RAG 参与预约写操作。

#### 用户做了什么

- 实现轻量级馆规 RAG。
- 使用本地 384 维字符 n-gram 哈希向量和内存向量库检索公告/馆规文本。
- 未命中时返回固定兜底话术，降低编造风险。
- 使用双 ChatClient：booking 链路绑定 Tool，rules 链路不绑定 Tool。

#### 直接产出

- 预约类问题优先走 Tool；馆规类问题优先走 RAG。
- RAG 不参与预约写操作，预约信息只信 Tool，馆规信息只信检索片段。

### 发生了什么：高并发预约库存

#### 为什么开始

预约系统在热门时段会出现并发抢票，需要防止超卖、重复预约和缓存数据库不一致。

#### 用户做了什么

- 设计 Redis Lua 原子预扣 + MySQL 事务落单链路。
- 使用 `booking:stock:{timeMark}` 管理时段库存。
- 使用 `booking:booked:{day}:{identityId}` 实现一证一约。
- MySQL 侧通过 `SUCC_CNT += delta` 原子记账。
- 落单失败或取消预约时，通过 Lua 回补库存并清理 booked 标记。

#### 直接产出

- Redis 侧在一次 Lua 脚本中完成判余票、判一证一约、扣库存、写 booked。
- MySQL 侧维护成功预约数，形成 Redis 剩余库存 + 数据库成功数 = 限额的约束。

#### 发生后的结果

- 2026-08-16 JMeter 压测：80 并发抢同一 `timeMark`、`LIMIT_CNT=50` 时成功 50 单，业务失败约 30，0 超卖。
- 同一 `identityId` 10 并发仅 1 单成功。

### 发生了什么：业务闭环和管理端

#### 用户做了什么

- 实现二维码核销、预约成功消息、爽约扫描、自动拉黑/解禁和管理端统计看板。
- 管理侧支持排期配置、预约核销、黑名单、公告、统计看板和 Excel 导出。
- 移动端包含 AI 咨询和 ONNX 文物识别入口。

### 结果和数据

- JMeter 80 并发、`LIMIT_CNT=50`：成功 50 单、0 超卖。
- 同一身份 10 并发：仅 1 单成功。
- RAG 使用 384 维本地字符 n-gram 哈希向量，不依赖 DeepSeek embedding。
- 项目文档记录后端 Spring Boot 3.4.5 / Java 17，管理端 Vue 3.5 / Vite 7 / Element Plus，小程序 21 页 / 4 TabBar。
